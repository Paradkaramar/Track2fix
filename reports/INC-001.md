## Observed Symptoms

- `POST /payments` requests for non-USD currency payments returned HTTP 500.
- USD-only payments were unaffected and returned HTTP 200.
- Error responses contained only `{"detail": "Internal Server Error"}`.
- Failures were reproducible and consistent across multiple request IDs:
  `req-1842` (250.0 EUR), `req-1844` (430.0 EUR), `req-1849` (130.0 EUR).
- No customer-facing error detail was surfaced.

---

## Investigation Summary

Four independent read-only investigators analyzed the incident in parallel:

1. **Log Investigator** — Read `incidents/INC-001-logs.json`. Reconstructed the runtime
   event sequence for `req-1842`. Observed `TypeError: unsupported operand type(s) for *:
   'float' and 'NoneType'` at `app/payment.py:16` in `convert_currency`. Identified two
   additional request IDs with identical failure patterns.

2. **Code Investigator** — Traced the execution path from `POST /payments` through
   `process_payment → convert_currency`. Observed that `config.get("EXCHANGE_RATE")`
   returns `None` when the key is absent, and that the result is used immediately in an
   arithmetic multiplication with no guard. Noted `config/prod.yaml` lacks `EXCHANGE_RATE`
   while `config/dev.yaml` contains it.

3. **Documentation + Configuration Investigator** — Read all `docs/` files and both
   config files. Confirmed `EXCHANGE_RATE` is documented as **required** in
   `docs/configuration.md`. Confirmed the key is absent from `config/prod.yaml`.
   Noted the documentation explicitly warns that missing required keys cause runtime
   failures.

4. **Test Investigator** — Read all test files. Confirmed all payment tests use
   development configuration exclusively (`conftest.py` fixture). No test exercises
   `POST /payments` with production configuration. Identified this as the gap that
   allowed the defect to reach production undetected.

All four investigators independently converged on the same root cause. No conflicting
evidence was identified.

## Root Cause

`EXCHANGE_RATE` is absent from `config/prod.yaml`. When the production environment
received a `POST /payments` request for a non-USD currency, `app/payment.py:15` called
`config.get("EXCHANGE_RATE")` which returned `None`. The unguarded multiplication on
line 16 — `float(amount) * None` — raised `TypeError`, which the global exception
handler converted to HTTP 500.

## Remediation

Two minimal code changes. No configuration files modified. No documentation modified.

### Change 1 — `app/payment.py`: Defensive guard on missing rate

Added a `None` check after `config.get("EXCHANGE_RATE")`. If the key is absent, raises
`ValueError` with a clear, actionable message instead of allowing `TypeError` to propagate.

```python
rate = config.get("EXCHANGE_RATE")
if rate is None:
    raise ValueError(
        "EXCHANGE_RATE is not configured for the active environment. "
        "Non-base-currency payments cannot be processed."
    )
converted = float(amount) * rate
```

### Change 2 — `app/main.py`: Handle `ValueError` from payment layer

Added `try/except ValueError` around `convert_currency` in `process_payment`. When the
payment layer raises `ValueError` (missing config), the route returns HTTP 422 with the
error detail rather than falling through to the generic HTTP 500 handler.

```python
try:
    amount_usd = convert_currency(req.amount, req.currency, cfg)
except ValueError as exc:
    logger.error("payment.config_error request_id=%s error=%s", request_id, str(exc))
    return JSONResponse(status_code=422, content={"detail": str(exc)})
```

## Documentation Impact

**Decision: No update required.**

`docs/configuration.md` line 28–29 already states: *"Missing or `null` values for
required keys will cause runtime failures when the affected code path is exercised."*
This remains accurate — a missing `EXCHANGE_RATE` still causes a failure (now HTTP 422
instead of 500). The fix changes *how* the failure is surfaced, not the documented
requirement that the key must be present. No documentation changes were made.

## Configuration Impact

**Decision: No configuration changes made.**

`config/prod.yaml` still lacks `EXCHANGE_RATE`. The fix makes the application respond
gracefully to that absence. Adding a production value for `EXCHANGE_RATE` is a business
decision (the correct rate is not determinable from repository evidence) and is outside
the scope of this remediation.

## Remaining Risks

- `config/prod.yaml` still lacks `EXCHANGE_RATE`. Non-USD payments in production will
  receive HTTP 422 (explicit, handled) rather than 200 until the correct production
  exchange rate is supplied. This is an intentional deferral — the value is a business
  decision outside the scope of code remediation.
- No startup-time validation of required configuration keys exists. A misconfigured
  deployment will only fail at the point of the affected request, not at service start.
  Adding startup validation would be a future improvement.
